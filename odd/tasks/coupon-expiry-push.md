# Coupon expiry push reminders
Objective: help reserved coupons turn into in-store redemptions. Branch: `feat/clientes-coupon-expiry-push` (T1 committed locally as `9b3ef04`).
Delivery: `ask-on-risk`, `feature-branch-chain`; forecast ~850 authored changed lines before generated migrations. Local slices: T1 policy → T2 registration → T3 worker → T4 mobile; no push or PR authorized. Runners: backend `tsx --test`, Clientes Jest.

## Specs

- **S1 — Push delivery.** User choice: “Notificación push (Recommended)”. Send one notification before expiry even if Clientes is closed, only for a still-reserved coupon. Reuse the backend's coupon calendar and recheck the reservation before sending. Working default: the local calendar day before expiry; no reminder after the coupon expires.
- **S2 — Open the coupon.** Accepted proposal: “Al tocarlo, la persona vuelve al cupón y ve la tienda, cuándo vence y cómo abrir el QR.” Use the authenticated wallet; push data must not contain a QR or personal details.
- **S3 — Measure the pilot.** Accepted proposal: “Compararía **qué porcentaje de los cupones reservados se canjea antes de vencer** entre un grupo con aviso y otro sin aviso.” Compare equally eligible reservations in stable user-level groups after expiry; distinguish assignment from provider acceptance.

Design: `coupon_expiry_reminders` (migration `0012_coupon_expiry_reminders`, additive; apply it before running the job, and `0011` before deploying the current logout code) holds one row per reservation, keyed by claim, for both arms. A single SQL definition of "may be reminded" (unreleased `claimed` coupon expiring tomorrow via `couponCalendarToday()`, active/verified/18+ client, device on a live session family of the same user) feeds assignment, acquisition and the pre-send recheck. Paused coupons and deactivated stores are still reminded because redemption does not check them either. Acquisition is one atomic statement (`for update skip locked`, oldest first, so batches and overlapping runs neither duplicate nor starve a row). The provider is called once with a 5 s timeout, no retry, and acquisition is never rolled back after a call; Expo `expiration` is the end of the coupon day in the coupon calendar. Outcomes: `accepted` (ticket only, not delivery), `rejected`, `unknown` (timeout, 5xx, or a crashed `sending` row older than 15 min), `skipped` (eligibility lapsed before any request). `DeviceNotRegistered` deletes the device only if the row is still identical to the one sent to. Sending requires `COUPON_EXPIRY_REMINDERS_SEND=true`; `report` is read-only. Report per arm over mature reservations: assigned (denominator), redeemed in window (assignment day to validity end), redeemed before window, accepted, rejected, unknown, sending, not attempted.
